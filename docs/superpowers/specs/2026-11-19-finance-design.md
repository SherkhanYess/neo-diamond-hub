# Вкладка «Финансы»: финмодель, ДДС по фондам, план-факт

Дата: 2026-11-19. ТЗ владельца: `~/Downloads/ТЗ финансовая система Neo Diamond.pdf` (17.11.2026),
эталон ДДС: `~/Downloads/DDS-fondy-sentyabr-2026.xlsx`.

## Зачем

Один вопрос: идём ли мы по плану в деньгах, и если нет — в каком фонде дыра.
Три блока на одном списке фондов:

1. **Финмодель (план)** — выручка, продажи, средний чек и раскладка каждого тенге по фондам.
2. **ДДС по фондам (факт)** — каждая операция Adesk по дням, разложенная по тем же фондам.
3. **План-факт по неделям** — сколько закладывали, сколько потратили, отклонение в ₸ и %.

## Решения владельца (19.11.2026)

- Учёт **общий на компанию**: Neo Diamond и taena в одной финмодели и одном ДДС, как в Adesk.
  Переключатель бренда на «Финансы» не действует.
- **Продажи и выручка — из Adesk.** Заказы — сделки с четырёхзначным кодом; продажи из наличия —
  проект «Товар под реализацию — …». ДДС поступлений ведётся по этим двум направлениям.
- Продажи из наличия **склеиваются автоматически** из платежей и **сверяются с amoCRM**.
  Позже в amoCRM появится признак «на заказ / в наличии» — тогда берём его.
- Поступление без статьи — **сверяем с возвратом на ту же сумму**.
- План выручки финмодели — **свой**, отдельно от «Планирования»; рядом показываем расхождение.
  Объединение — позже.
- В план-факте план месяца по любой строке можно **вписать вручную**, отдельно от финмодели.
- Доступ — владелец плюс **право «Финансы»**, которое выдаётся в «Настройках».
- **Привязка статей Adesk к фондам — отдельный раздел «Настроек».**
- **Сумма на одну продажу по факту считается автоматически** — только у фондов, чья логика
  «на продажу» (признак фонда `per_sale`; сейчас сдельная ЗП, закупки, транспортные):
  оплачено ÷ число продаж (KPI маркетолога 400 000 / 40 сделок = 10 000 ₸). Признак можно
  включить другому фонду в настройках.

## Архитектура

Как amoCRM и Meta: копия источника в Supabase + чистые JS-движки с тестами + страницы React.

```
Adesk API ──adesk-sync (pg_cron, 15 мин)──▶ adesk_* таблицы
                                               │
     fin_funds / fin_items / fin_rules ────────┤  (настройки)
     fin_models / fin_plan_overrides ──────────┤  (план)
                                               ▼
              src/lib/finance/*.js (classify → sales → dds → model → planfact)
                                               ▼
                       /finance: Финмодель · ДДС · План-факт
                       /settings: Привязка статей к фондам
```

### Adesk

- API v1 `https://api.adesk.ru/v1/…?api_token=`; токен — `~/.config/neo-diamond-hub/adesk_token`
  и секрет `ADESK_TOKEN`. В репозиторий не попадает.
- Используем: `bank-accounts`, `transactions/categories`, `projects`, `transactions`
  (`range=custom&range_start=YYYY-MM-DD&range_end=…&length=1000`).
- Проверено 19.11: сентябрь — 401 операция (как в эталоне); поступления до эквайринга и возвратов
  53 189 574 = эталон; чистый поток −6 167 228 против −6 167 237 в эталоне (округление курса).
- Edge Function `adesk-sync` (только чтение Adesk): справочники целиком, операции — последние
  60 дней на каждом запуске (задним числом правят), режим `{from,to}` для догрузки. Первая загрузка
  с 2026-08-01. Удалённые в Adesk операции удаляются и у нас (сверка id в окне).
- Таблицы: `adesk_accounts`, `adesk_categories`, `adesk_projects`, `adesk_transactions`
  (ключевые колонки + `raw jsonb`). Сумма в тенге: `amount` для KZT, `amount × exchangeRate`
  для валютных счетов (курс операции Adesk). Ошибки — `integrations.last_error` (key `adesk`).

### Справочники (настройки)

- `fin_funds` — единый список фондов: блок (`variable` / `management` / `fixed`), способ расчёта
  (`pct_revenue`, `pct_revenue_per_sale`, `pct_margin`, `fixed_month`, `salaries`), признак
  `per_sale` (считать «на одну продажу»; по умолчанию у сдельной ЗП, закупок, транспортных), порядок.
  Начальный список — из ТЗ: налоги, ЗП % от продаж, сдельная ЗП, закупки, транспортные;
  дивиденды (с благотворительностью), развитие, резерв, реклама и продвижение; аренда
  (Алматы / Астана), коммунальные (содержание офиса), оклады, прочие. Фонда оплаты долгов нет.
- `fin_items` — строки внутри фонда (Бриллианты, Аренда Астана, «Алмас — консультант», Amo CRM…).
- `fin_rules` — как операция попадает в строку, по приоритету:
  1. исключённые проекты (статуэтка «9612 сентябрь Статуетка» — отовсюду, включая продажи);
  2. переводы между счетами — не доход и не расход (отдельно только курсовая разница);
  3. особые правила: счёт без статьи («Фонд маркетинга (долларовый счёт)» → реклама),
     описание (Аренда → Астана), имя человека в описании (ФОТ → строка человека);
  4. статья Adesk → строка фонда;
  5. иначе — «Не распределено» (видно, не теряется).
- Делёж выплат «сверх оклада»: выплата человеку сверх его оклада из финмодели уходит в
  указанный фонд (продажники → ЗП % от продаж; Наргиза: KPI → сдельная, «Доля от продаж» →
  ЗП % от продаж; маркетологи → сдельная). Правило хранит человека, оклад берётся из модели месяца.
- Экран «Привязка статей к фондам» в «Настройках» (право `finance`): все статьи Adesk с текущим
  фондом, новые сверху, особые правила списком. Новую статью привязываешь один раз.

### Продажи и выручка (`sales.js`)

- **Заказ** = сделка Adesk (`type=deal`, имя начинается с 4 цифр). Месяц продажи — `actDate`.
  День продажи для недель: `actDate`, а если это последний день месяца (дата по умолчанию у
  бухгалтера) — дата первой оплаты сделки в этом месяце. Выручка — сумма сделки
  (`dealAmount`), если пусто — сумма поступлений по сделке.
- **Из наличия** = поступления проектов «Товар под реализацию — …», склеенные в продажи: платежи
  с похожим описанием (общие слова модели/карата) в пределах 7 дней — одна продажа. Затем
  сверка с закрытыми сделками amoCRM (сумма ±5 %, дата ±7 дней): совпадение подтверждает
  продажу, расхождение показывается рядом со счётчиком. Ошибка ±1–2 продажи допустима.
- Возврат клиенту уменьшает поступления и (если продажа месяца отменена целиком) число продаж.
- Поступление без статьи и сделки: ищем возврат на ту же сумму (±7 дней) — пара гасится;
  иначе — «Не распределено».
- Средний чек = выручка ÷ продажи.

### ДДС по фондам (`dds.js`)

Деньги стоят в день операции Adesk. Строки сверху вниз:

1. Остаток на начало дня (все счета; из остатков Adesk минус последующие операции).
2. Поступления: **заказы / из наличия / прочее**, внутри — нал («Наличные (тенге)»,
   «Наличные (доллар)», «Цифровая наличка») и безнал (Kaspi Pay, Online Bank); минус эквайринг
   («Комиссия за Pay»); минус возвраты клиентам.
3. Платежи — фонды и их строки; «Не распределено».
4. Чистый денежный поток.
5. Курсовые разницы при переводах.
6. Остаток на конец дня — сходится с Adesk.

Столбцы: итог месяца, % от поступлений, каждый день с днём недели.
Платёж за прошлый месяц помечается по дате начисления Adesk (`relatedDate` в прошлом месяце).

### Финмодель = уровень необходимости (`model.js`)

**Уточнение владельца 19.11:** это не финмодель с вводимой выручкой, а «уровень необходимости».
Выручка не вводится — она результат: сколько должна сделать компания, чтобы покрыть дивиденды и
развитие (задаются суммой — «мой уровень необходимости»), постоянные расходы, оклады и фонды в %.
Благотворительность — из дивидендов. Вкладка называется «Уровень необходимости». Пункты ниже
про «вводим выручку» заменены этим правилом.

- Хранится по месяцам (`fin_models`: месяц, выручка, средний чек, % фондов, нормы на продажу,
  постоянные суммы, оклады по людям). Новый месяц создаётся копией прошлого; старые не меняются.
- Вводим: план выручки, средний чек, % каждого фонда, нормы ₸ на продажу, постоянные суммы,
  оклады. Считается: продажи = выручка ÷ чек, суммы фондов, суммы на продажу, маржа
  (выручка − прямые переменные), фонды управления от маржи, итоги блоков — только формулами
  (две ошибки итогов из ТЗ исчезают сами).
- Рядом с нормой на продажу (у фондов `per_sale`) — **факт прошлого месяца на продажу**
  (из ДДС ÷ продажи Adesk).
- Сверху — расхождение плана выручки с «Планированием» (сумма планов брендов).

### План-факт по неделям (`planfact.js`)

- Строки: выручка, количество продаж, средний чек, фонды в порядке модели, маржа, остаток.
- Столбцы: недели месяца (первая и последняя неполные) и итог месяца; в каждой — план, факт,
  отклонение ₸, отклонение %, доля от выручки план/факт, на одну продажу план/факт (фонды `per_sale`).
- План недели:
  - выручка и продажи — план месяца по дням недели пропорционально; распределение правится вручную;
  - переменные фонды — плановый % × **фактическая** выручка недели; рядом вариант от плановой;
  - фонды управления — плановый % × фактическая маржа;
  - постоянные — сумма модели в неделю платежа по графику (по умолчанию — даты прошлого месяца).
- **Ручной план месяца** по любой строке (`fin_plan_overrides`) заменяет расчётный; расчётный
  виден рядом.
- **На одну продажу (факт)** = факт ÷ продажи периода — только у фондов `per_sale`, по фонду и
  по каждой его строке (KPI маркетолога, курьер…). У остальных фондов столбец пустой.
- Нарастающий итог с начала месяца и остаток лимита до конца месяца.
- Цвет: зелёный — в пределах плана, жёлтый — перерасход до 10 %, красный — больше 10 %;
  для выручки и маржи наоборот.
- Клик по отклонению — операции, которые его дали. Платежи за прошлый месяц помечены и не
  выглядят перерасходом.

## Доступ

Новое право `finance` (видит и редактирует «Финансы» и привязку статей). У системной роли
владельца — по умолчанию. Выдаётся любой роли в «Настройках». RLS на `adesk_*` и `fin_*` —
только с правом `finance`.

## Проверка готовности

- ДДС за сентябрь 2026 из Adesk = эталон ТЗ без статуэтки: поступления 50 189 574
  (нал 27 473 574, безнал 22 716 000), выплаты с эквайрингом и возвратами 59 324 471, сальдо с
  курсовыми −9 170 575 ₸ (до округления курса). Тест на сохранённой выгрузке сентября.
- Остаток на конец месяца совпадает с Adesk.
- Новый месяц заполняется без ручного переноса: план вводим, факт приходит из Adesk.
- Нераспределённые статьи и операции без статьи видны отдельной строкой.
- В план-факте по каждому фонду: отклонение ₸ и %, доля от выручки, остаток лимита; у фондов
  `per_sale` — сумма на одну продажу.
- Поменяли процент в модели — пересчитался план-факт.
