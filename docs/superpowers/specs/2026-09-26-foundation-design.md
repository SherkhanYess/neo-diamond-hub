# Информационный центр Neo Diamond — Фаза 1: Фундамент

Дата: 2026-09-26 · Автор: Шерхан · Проект: neo-diamond-hub

## Контекст

Единый информационный центр Neo Diamond строится фазами по зависимости данных:
**Фундамент → Планирование → Маркетинг+Продажи (факт) → Журнал решений → Performance.**
Этот спек покрывает только **Фундамент**. Каждая последующая фаза получает
собственный цикл brainstorming → spec → plan.

Фундамент даёт то, на что опираются все модули: проект и стек, авторизацию,
роли и права, справочники, каркас приложения с меню и модуль «Настройки».
Требование ТЗ — архитектура ролей, филиалов и периодов должна выдержать
поздние модули без переделки.

## Границы фазы

**В фазе:** проект/стек, Supabase Auth (email+пароль) + RLS, модель ролей и прав,
справочники + слой API, каркас приложения (меню, роутинг, заглушки разделов),
модуль «Настройки» (справочники + доступ + отображение), тесты.

**Вне фазы:** интеграции amoCRM/Meta/TikTok и их API, маппинг первого касания,
поля сделки, правила кампаний, теги креативов, права планирования, панель
фильтров отчётов, сами отчётные страницы, дашборды, журнал решений, Performance.

## Стек и репозиторий

- Новый репозиторий `neo-diamond-hub`. Стек копируется с `neo-diamond-ops`:
  React 19 + Vite + `@supabase/supabase-js` + Vitest + Netlify.
- Токены брендбука `src/styles/tokens.css` переносятся из `neo-diamond-ops` 1:1.
  Шрифты Unbounded / Manrope / JetBrains Mono — Google Fonts.
- Новый Supabase-проект со своими кредами в `.env`
  (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`). `neo-diamond-ops` не трогаем.
- Роутинг: `react-router` (настоящий роутер под многостраничность),
  а не ручные табы как в старом проекте.
- Netlify: `netlify.toml` + переменные окружения на сайте.

## Модель данных (Supabase, PostgreSQL)

Все таблицы под RLS. Миграции — нумерованные SQL-файлы в `supabase/migrations/`.

### Авторизация и доступ

- **profiles** — `id` (= `auth.users.id`, PK/FK), `full_name`, `role_id` (FK roles),
  `is_active` (bool, отключение без удаления), `created_at`.
- **roles** — `id`, `name`, `is_system` (bool, системные роли не удаляются),
  `caps` (`text[]` — набор прав), `scope_type` (`'all' | 'branches'`),
  `is_archived`, `sort_order`, `created_at`.
  - Права (caps): `view_reports`, `enter_fact`, `edit_plan`, `approve_plan`,
    `decisions`, `settings`. Список прав — константа в коде; роли выбирают из него.
- **role_branches** — `role_id`, `branch_id`. Ограничение роли филиалами
  (только при `scope_type='branches'`).
- **profile_branches** — `profile_id`, `branch_id`. Персональное ограничение
  филиалами поверх роли (для случая «роль общая, но конкретный юзер — на филиал»).

Итоговая область пользователя = пересечение области роли и персональной области
(если персональная задана). Хелпер БД `current_branch_ids()` возвращает список
доступных пользователю `branch_id`; `current_caps()` — набор прав.

### Справочники (единая форма)

Общие поля каждого справочника: `id`, `name`, `sort_order`, `is_archived`,
`created_at`. Специфичные поля указаны отдельно.

- **cities** — города.
- **branches** — `city_id` (FK). Филиалы.
- **client_tasks** — `segment` (свёртка: Помолвка / Подарок / Для себя /
  Значимое событие). Шесть стартовых задач.
- **demand_sources** — `default_owner_id` (FK profiles, nullable).
  Performance, Контент, Influence, Walk-in, TikTok-эфир, CRM-маркетинг.
- **lead_sources** — источники лида (последнее касание).
- **funnel_stages** — `is_qualification` (bool), `is_sale` (bool). Порядок этапов
  через `sort_order`. Семь стартовых этапов; ровно один с `is_qualification`,
  ровно один с `is_sale`.

Поля привязки к amoCRM (`crm_status_id` для этапов, `crm_value` для источников
лида) закладываются в схему как nullable-колонки, но UI их редактирования —
в поздних фазах. В фазе 1 колонки создаются, но не заполняются.

### Настройки отображения и аудит

- **display_settings** — одна строка на компанию: `plan_color_low`,
  `plan_color_ok`, `plan_color_high` (пороги % выполнения), `currency`,
  `week_start` (0/1). Значения по умолчанию из брендбука/ТЗ.
- **audit_log** — `id`, `actor_id`, `entity` (имя таблицы/раздела),
  `entity_id`, `action` (`create|update|archive|delete`), `diff` (jsonb),
  `created_at`. Пишется при изменениях в «Настройках».

### RLS

- Чтение справочников: любой аутентифицированный пользователь (данные общие).
- Запись справочников, ролей, профилей, display_settings: только право `settings`.
- `branches`/`cities` фильтруются областью только там, где это осмысленно;
  сами справочники общие для чтения.
- Хелпер-функции `current_caps()` и `current_branch_ids()` — SQL `security definer`,
  читают `profiles`/`roles`/`*_branches` по `auth.uid()`.

### Правила архива и удаления

- Элемент справочника **удаляется**, только если не используется ни в одной
  зависимой записи. В фазе 1 зависимостей от данных ещё нет; helper
  `is_reference_in_use(entity, id)` возвращает false, но расширяется в поздних
  фазах (проверка FK на сделки/планы/расходы).
- Если используется — только **архивирование** (`is_archived=true`). Архивные
  не предлагаются при вводе, остаются видны в отчётах прошлых периодов.
- Удаление и архивирование — с окном подтверждения и тостом «Отменить»
  (несколько секунд на откат).

### Seed

Миграция сидов создаёт: 6 клиентских задач со свёртками, 6 источников спроса,
7 этапов воронки (с флагами квалификация/продажа), системную роль «Владелец»
(все caps, `scope_type='all'`, `is_system=true`), строку display_settings
по умолчанию. Первый пользователь-владелец заводится вручную через SQL
(документируется в README), т.к. на старте некому его пригласить.

## Каркас приложения

- **Левое меню**: Рабочий стол, Планирование, Маркетинг, Продажи,
  Журнал решений; внизу отдельно — Настройки; ниже — профиль + выход.
  Сворачивается бургером до колонки иконок; на телефоне открывается оверлеем
  поверх страницы.
- **Пункты без соответствующего права у роли не отображаются.** Настройки
  видны только при праве `settings`.
- **Верх рабочей области**: заголовок страницы + слот под панель фильтров и
  переключатель периода. Сам фильтр строится в фазе отчётов; в фазе 1 слот пуст.
- **Заглушки разделов**: Рабочий стол, Планирование, Маркетинг, Продажи,
  Журнал решений в фазе 1 показывают пустое состояние с объяснением
  («Модуль появится в следующей фазе»), а не пустой экран (UX-правило ТЗ).
- **Роутинг**: `react-router`; защищённые маршруты (редирект на /login без сессии);
  маршрут скрывается/возвращает 403-состояние без нужного права.

## Модуль «Настройки»

- SaaS-паттерн: боковое подменю разделов + рабочая область с поиском,
  добавлением, редактированием, архивированием.
- **Разделы фазы 1**: Пользователи, Роли и права, Города и филиалы,
  Клиентские задачи, Источники спроса, Источники лида, Воронки, Отображение,
  Журнал изменений.
- **Переиспользуемый `CrudSection`**, управляемый конфигом на раздел
  (колонки таблицы, поля формы, валидация, правила архива, связанный API).
  Простые справочники (города, задачи, источники, этапы) описываются конфигом;
  сложные разделы (Пользователи, Роли и права) — отдельные компоненты, но с тем
  же визуальным паттерном.
- **Пользователи**: приглашение (создание в Supabase Auth + profile),
  отключение (`is_active=false`, не удаление), назначение роли и филиалов.
- **Роли и права**: редактируемая матрица caps × роль, `scope_type` и филиалы,
  создание своих ролей. Системная роль «Владелец» не удаляется.
- **Воронки**: этапы, порядок (drag или sort_order), флаги «квалификация»/
  «продажа» с валидацией «ровно один каждого».
- **Отображение**: пороги цвета выполнения плана, валюта, начало недели.
- **Журнал изменений**: read-only лента из `audit_log` с фильтром по разделу.
- Разрушающие действия — подтверждение + тост «Отменить».
- Доступ ко всему модулю — только право `settings`.

## Слой API (клиент)

- `src/lib/supabaseClient.js` — как в `neo-diamond-ops`.
- `src/lib/api/*` — по модулю на сущность (`auth`, `profiles`, `roles`,
  `references` (обобщённый CRUD по справочникам), `settings`, `audit`).
- Права дублируются: клиентский хелпер `can(cap)` прячет меню/кнопки,
  RLS — единственный настоящий барьер данных.

## Тестирование

- Vitest + Testing Library (как в `neo-diamond-ops`).
- Юнит-тесты: маппинг `caps` → видимость пунктов меню и кнопок; правила
  архива/удаления справочника; валидация форм (уникальность имени, «ровно один
  этап квалификации/продажи», сумма сортировки); пересечение областей филиалов.
- Правило «всё по токенам брендбука»: компоненты берут цвета/шрифты/радиусы/тени
  только из `tokens.css`; никаких хардкод-цветов.

## Критерии приёмки фазы 1

- [ ] Вход по email+паролю через Supabase Auth; без сессии — редирект на /login.
- [ ] Роль с ограниченным набором caps не видит скрытые пункты меню; RLS не отдаёт
      данные без права `settings` при попытке записи.
- [ ] Новый филиал / источник спроса / этап добавляется в «Настройках» без правки
      кода и сразу доступен (в фазе 1 — в самих «Настройках»).
- [ ] Использованный элемент справочника нельзя удалить — только архивировать;
      архивный не предлагается при вводе.
- [ ] Разрушающие действия дают подтверждение и тост «Отменить».
- [ ] Левое меню сворачивается бургером; на телефоне 390px открывается оверлеем.
- [ ] Заглушки будущих модулей показывают объяснение, а не пустой экран.
- [ ] Роль «Владелец» — системная, не удаляется; можно создать кастомную роль.
- [ ] Все экраны используют только токены брендбука.
- [ ] Изменения в «Настройках» попадают в Журнал изменений.
