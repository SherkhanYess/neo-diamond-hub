# Фаза 2: Планирование — дизайн

Дата: 2026-09-26 · Проект: neo-diamond-hub

## Контекст

Модуль «Планирование» — сердце платформы. Логика сверху вниз: план выручки →
план по клиентским задачам → нужное число заказов → нужный бюджет по источникам.
Пользователь заполняет два листа (Маркетинг | Продажи), утверждает — план
становится колонкой «План» на страницах отчётов и на рабочем столе.

Опирается на фундамент (фаза 1): роли/права (`edit_plan`, `approve_plan`),
справочники (клиентские задачи, источники спроса, филиалы, этапы воронки),
`audit_log`.

## Границы фазы

**В фазе:** страница «Планирование», расчётный движок, лист «Маркетинг»
(ввод + расчёт), лист «Продажи» (конверсии + разворот заказов), проверки при
вводе, черновик/утверждение с версиями и причиной, копирование плана прошлого
месяца, окно подтверждения с итогами. Права `edit_plan` (маркетинг) и план ОП
(РОП). Пункт меню «Планирование».

**Вне фазы:** отображение плана на страницах Маркетинг/Продажи/Рабочий стол
(фаза 3 — там план встаёт рядом с фактом), факт из amoCRM, любые интеграции.
В этой фазе план виден и утверждается только на самой странице «Планирование».

## Расчётная модель (где что считается)

Формулы живут в JS-модуле `src/lib/planning/calc.js` (чистые функции, без
побочных эффектов, полностью покрыты тестами). Так таблица пересчитывается
мгновенно при вводе, и расчёт проверяется юнит-тестами против эталона.

БД хранит **только введённые значения** (inputs) и **снимок расчёта на момент
утверждения** (computed snapshot, jsonb). Отчёты будущих фаз читают снимок,
а не пересчитывают.

### Лист «Маркетинг» — ввод

- На уровне клиентской задачи: `target_revenue` (целевая выручка),
  `ad_budget_pct` (% рекламного бюджета от выручки).
- На уровне задача × источник спроса: `revenue_share` (доля выручки источника
  внутри задачи, %), `avg_check` (средний чек), `ad_budget` (рекламный бюджет
  источника; по умолчанию = выручка источника × % задачи, переписывается вручную),
  `owner_id` (ответственный).

### Лист «Маркетинг» — расчёт (формулы)

| Показатель | Формула |
| --- | --- |
| Общий бюджет задачи | target_revenue × ad_budget_pct |
| Выручка источника | target_revenue задачи × revenue_share источника |
| Заказы | выручка источника ÷ avg_check |
| CAC (план) | ad_budget источника ÷ заказы |
| ROAS (план) | выручка ÷ ad_budget |
| Нужное число лидов по этапам | заказы, развёрнутые назад через конверсии листа «Продажи» |

Заказы внутри расчётов не округляются; на экране — до одного знака. Итоговая
таблица «по источникам спроса» собирается автоматически.

### Лист «Продажи» — ввод и расчёт

- Подтягивается с листа «Маркетинг» (не редактируется здесь): суммарная выручка
  и число заказов на филиал.
- Вводится (на филиал): конверсии обращение→квалификация→встреча назначена→
  встреча состоялась→продажа; средний чек (по умолчанию — средневзвешенный из
  «Маркетинга»).
- Считается: плановое число сделок на каждом этапе — заказы, развёрнутые назад
  через конверсии. Это же число попадает в строку «Нужное число лидов по этапам».

Разворот: если заказы = N (число на этапе «Продажа»), а конверсия
этап_i→этап_{i+1} = c_i, то число на этапе i = число на этапе i+1 ÷ c_i.
Идём от продажи назад к обращению.

## Проверки при вводе

- Доли источников внутри задачи в сумме = 100%. Иначе план нельзя отправить на
  утверждение (кнопка заблокирована, показывается расхождение).
- Сумма целевых выручек задач сравнивается с целевой выручкой филиала;
  расхождение показывается (не блокирует — это ориентир).
- Конверсии в (0, 1]. Средний чек > 0.

## Модель данных (миграция 0006_planning.sql)

- **plans** — `id`, `month` (date, первое число), `branch_id` (fk), `version`
  (int), `status` (`draft`|`approved`), `reason` (text, обязателен при версии>1),
  `branch_target_revenue` (numeric, целевая выручка филиала — ориентир для
  проверки), `computed` (jsonb, снимок на момент утверждения; null у черновика),
  `created_by` (fk profiles), `approved_by` (fk profiles null), `approved_at`
  (timestamptz null), `created_at`. Уникальность: (month, branch_id, version).
- **plan_task_lines** — строки уровня задачи: `plan_id` (fk), `client_task_id`
  (fk), `target_revenue` (numeric), `ad_budget_pct` (numeric). Уникальность
  (plan_id, client_task_id).
- **plan_source_lines** — строки задача × источник: `plan_id`, `client_task_id`,
  `demand_source_id`, `revenue_share` (numeric %), `avg_check` (numeric),
  `ad_budget` (numeric null = авто), `owner_id` (fk profiles null). Уникальность
  (plan_id, client_task_id, demand_source_id).
- **plan_sales_conversions** — конверсии на филиал: `plan_id`, `from_stage_id`,
  `to_stage_id`, `rate` (numeric 0..1). Плюс `plan_sales_avg_check` хранится
  как поле на plans (`sales_avg_check` numeric null = авто).

### Статусы и версии

- Черновик: одна строка plans со status='draft' на (month, branch). Автосейв
  инпутов.
- Утверждение: помечает текущую версию approved, пишет `computed` снимок.
  «Изменить план» после утверждения создаёт **новый черновик как копию** с
  version+1; при повторном утверждении требуется `reason`.
- Отчёты читают max(version) where status='approved'.
- «Скопировать план прошлого месяца» — создаёт черновик текущего месяца из
  инпутов прошлого.

### RLS

- Чтение plans/*: `view_reports` или `edit_plan` или `approve_plan`.
- Запись инпутов (plan_task_lines, plan_source_lines, conversions, draft plans):
  `edit_plan`.
- Утверждение (перевод в approved, запись computed): `approve_plan`.
- Ограничение по филиалам через `current_branch_ids()`.

## Интерфейс

Страница «Планирование» (пункт меню, право `edit_plan` или `approve_plan`):

- Вверху: выбор месяца, города, филиала. Статус (Черновик/Утверждён vN).
- Внизу — переключатель листов: **Маркетинг | Продажи** (как вкладки таблицы).
- **Лист «Маркетинг»**: редактируемая сетка. Группировка по клиентской задаче;
  под каждой задачей строки источников; итог по задаче; внизу автособираемая
  таблица «по источникам спроса». Ячейки плана редактируются прямо в таблице,
  моноширинные цифры, ₸ с пробелами, right-align. Живой пересчёт.
- **Лист «Продажи»**: конверсии по этапам (ввод) + рассчитанное число сделок на
  каждом этапе; средний чек.
- Кнопка **«Утвердить»** закреплена внизу, утверждает оба листа вместе. Перед
  утверждением — окно подтверждения с итогами: выручка, бюджет, заказы, CAC, ROAS.
  Заблокирована, если доли источников ≠ 100%.
- Если план утверждён — режим просмотра + кнопка «Изменить план» (создаёт версию).
- Пустой экран, если план не заведён: кнопка «Создать план» / «Скопировать
  прошлый месяц».
- Всё по токенам брендбука; редактирование ячеек, навигация с клавиатуры.

## Тестирование

- Юнит-тесты `calc.js`: выручка источника, заказы (без округления), CAC, ROAS,
  разворот лидов по конверсиям, средневзвешенный чек, сумма долей, итоги по
  источникам. Эталон — пример из ТЗ (Алматы), проверка совпадения заказов/CAC/ROAS.
- Тесты валидаций: доли=100%, конверсии в диапазоне.
- Тест версий: утверждение пишет снимок; «изменить» создаёт version+1 с reason.

## Критерии приёмки

- [ ] План месяца по таблице маркетинга вводится в платформе и даёт те же
      заказы, CAC, ROAS, что и таблица.
- [ ] Доли источников ≠ 100% блокируют утверждение.
- [ ] Утверждённый план нельзя изменить без новой версии с причиной.
- [ ] Число лидов по этапам = заказы, развёрнутые назад через конверсии.
- [ ] Можно скопировать план прошлого месяца как черновик.
- [ ] Утверждение пишет снимок computed, доступный отчётам следующих фаз.
- [ ] Права: edit_plan вводит, approve_plan утверждает; ограничение по филиалам.
